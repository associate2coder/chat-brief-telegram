## Findings

### [stage-1] Oversized request body escapes the always-200 envelope entirely
- **File:line:** `src/http/app.ts:12-18`
- **AC:** AC-02 (+ ADR-0002; `contracts/openapi.yaml:57` documents only a `200` response)
- **Problem:** The error middleware only converts `SyntaxError`. Any other `express.json()`
  error (e.g. `PayloadTooLargeError` on a body over Express's default ~100 KB limit) falls
  through to `next(err)` with no downstream handler, hitting Express's default error page.
  Verified live against `node dist/index.js`: a 150 KB body returns `HTTP 413`,
  `content-type: text/html`, with a stack trace (absolute repo paths, dependency internals) in
  the body and on stderr. Reachable unauthenticated, with no shared secret required — exactly
  the "non-2xx path whose body could be discarded" ADR-0002 exists to eliminate.
- **Resolution:** Fix now — handed to `implement` as a follow-up task.

### [stage-1] AC-05 detection misses the `chat not found` variant the SAD names
- **File:line:** `src/telegram/index.ts:15-21`
- **AC:** AC-05
- **Problem:** `isChatNotStartedError` matches only `error_code === 403` +
  `/can't initiate conversation/`. `sad.md:270` names the AC-05 branch as "chat not found / bot
  can't initiate" — Telegram's usual real-world response for an owner who never started a chat
  with the bot is `error_code 400` + `"Bad Request: chat not found"`. That path currently
  returns the generic failure wording instead of AC-05's required distinct wording. Uncovered by
  `src/telegram/index.test.ts:26-38` (only exercises the 403 string).
- **Resolution:** Fix now — handed to `implement` as a follow-up task.

### [stage-2] Authorization does not run before body parsing
- **File:line:** `src/http/app.ts:12-18`
- **AC:** AC-03 (spec §6.1: "the relay authenticates the caller via the shared secret before doing
  anything else")
- **Problem:** Verified live — a wrong-secret caller sending malformed JSON gets back
  `{"error":"request body must be valid JSON"}`, not `{"error":"unauthorized"}`. A minor
  information leak: an unauthenticated caller can distinguish body-parse state before learning
  it's denied.
- **Resolution:** Fix now — handed to `implement` as a follow-up task.

### [stage-2] A non-numeric `TELEGRAM_TIMEOUT_MS` silently breaks every send
- **File:line:** `src/config/index.ts:35-36`
- **AC:** n/a (spec §6 NFR "waits at most 5000 ms"; T1's fail-closed DoD)
- **Problem:** `Number(env.TELEGRAM_TIMEOUT_MS ?? 5000)` yields `NaN` for a typo'd value; Node
  coerces `setTimeout(..., NaN)` to 1 ms, so every send aborts almost instantly with no
  diagnostic — reported as a generic Telegram delivery failure. `PORT` has the same class of gap
  (empty string → binds a random port; non-numeric → `NaN`). The three credential fields already
  fail closed at boot; these two numeric fields don't.
- **Resolution:** Fix now — handed to `implement` as a follow-up task.
